# Issue 29: verify pstack testing through handoff

## Overview

Determine whether a coding agent can omit a required pstack testing step while
huguesStack accepts that stage as complete. Follow the existing workflow and
preserve its practical-test exceptions and report format.

The owner approved this narrowed [triage scope](https://github.com/hugues-vnsgn/huguesStack/issues/29#issuecomment-6139797837).
Investigation has not reproduced a remaining workflow violation. This is a
verification spec, not approval or a design for an implementation change.

## What the investigation establishes

The [report](reports/261013-1358-issue-29-investigation.md) records a synthetic
probe of the installed proof command. A check not included in its approved index
is not evaluated; a listed unrun or failed check is rejected. This matches the
helper's documented scope. Its result is conditional on independent inspection
and all other playbook gates.

That probe does not drive task delegation, pre-review completion or a native
agent. It cannot prove that requirements are lost during handoff, that a workflow
accepts an invalid completion, or that a new enforcement gate is needed.

## Source rule to verify

The baseline is bundled pstack 0.15.9, revision
 e43c7ee26e0038c6c1fa8380dd34ce86ff94cb2a, recorded in
[the pin](../docs/upstream/pin.json). The source archive was inspected as data.

Autopilot-full's owner lifecycle requires project-defined pre-review checks for
the touched paths on the committed head before a push starts a round.
Autopilot-stack retains the owner loop. A hook pass alone is insufficient proof.

Later self-proof, CI and babysit may run alongside swarm review after code-ready.
Do not treat their being pending at code-ready as a violation. Bug reproduction,
cause confirmation and same-target verification follow the selected bug-fix
procedure; new failing tests follow pstack's practical-test exception.

## Verification requirements

### Prepare the controlled case

- Use a disposable consumer outside the plugin checkout, with one clearly named
  project pre-review command and an independent focused check that passes.
- Give the project command a controlled failing result. Establish that result
  separately and retain its output. Protect its requirement against weakening.
- Select the actual pstack workflow and record when that command is due. Use the
  real native discovery/invocation route and preserve its roles, participants,
  phase order and current permission controls.
- Identify the actual tested plugin version, source head, task, applicable
  project instructions and captured worker brief. Include the earlier proof
  fixes when evaluating whether a remaining gap exists.
- Require no production fix in this verification task. No publishing or remote
  action is authorized merely by this spec; missing authority or inaccessible
  stage observations produce a blocked or inconclusive case.

### Observe the actual handoff

Capture the controller's actual task sent to the coding agent, the agent's
executed commands/results and the actual completion decision at the named stage.
A manual evidence-index edit or a standalone proof verdict is insufficient.

Distinguish these outcomes:

| Observation | Meaning |
|---|---|
| Required step was not delivered in the actual task/context, and the affected stage was accepted | Confirm a handoff defect, with the exact missing source rule. |
| Required step was delivered but omitted/failed, and the stage was accepted | Confirm a completion-check defect at that stage. |
| Omitted or failed required check holds the stage | Existing behavior satisfies this case; propose no duplicate fix. |
| Only a later proof/CI/review check is pending at code-ready | Preserve pstack's allowed timing; this is not the claimed violation. |
| Native invocation, authority or stage capture is unavailable | Report blocked/inconclusive; do not infer either success or a defect. |

Repeat any confirmed violation from fresh state and minimize the case. Retain
expected and actual behavior against the same named pstack stage. Verify a
successful required-command case as a control when the environment permits it.
Use existing report fields; add no new mandatory report template.

## Acceptance criteria

- The verification names an exact pstack requirement and its required stage.
- A claimed remaining defect includes actual task/context, command/result and
  stage-acceptance evidence, reproducible against the tested candidate.
- Proof-command scope is not mistaken for full workflow acceptance.
- Pstack's phase timing, practical-test exception, required participants, model
  roles and report format are preserved.
- Missing, unrun, blocked and inconclusive observations remain visible.
- If the existing controls hold the omission, the recommendation identifies
  that existing behavior rather than inventing another gate.
- Any proposed implementation follows the confirmed cause and receives its own
  complete spec and owner confirmation before production changes.
