## Requirements

### Select and protect the coverage

Record an explicit mobile profile in the approved committed program plan.
Within that profile, classify each PR as mobile behavior, tooling/workflow, or
documentation. Establish the classification from its actual diff and applicable
project instructions during independent review. An unknown classification holds
verification. Existing plans retain their previous rules until an operator
approves migration through the verification-contract gate.

For each PR, record affected platforms, changed areas, applicable risks and the
checks that cover them. Each check names its risk, reason, target, action,
observable pass condition and retained artifact. Use unique check IDs and allow
any positive number of justified live checks for mobile behavior, including 12.
Several risks may share a check when its actions and results actually cover them.
Worker concurrency and required reviewers remain governed by existing contracts.

Review every risk relevant to the declared changed areas. Mark it applicable,
not applicable with a reason, or unresolved. An applicable risk needs coverage
on each affected target. An unresolved risk or missing target check holds a clean
verdict. A reasoned exemption remains subject to the owner's contract approval;
it is not a passed check.

| Changed area | Coverage to assess when selecting checks |
| --- | --- |
| Navigation or saved screen state | Backgrounding, process death, reopening and restored navigation; relevant rotation or gesture transitions. |
| Layout or text | Smallest supported layout, large accessibility text, and realistic input/keyboard behavior where the changed interaction uses them. |
| Persistence | Read/write failure, corruption, interrupted writes and preservation of existing data. |
| Native view ownership | Repeated presentation/dismissal, memory retention and cleanup. |
| Launch, packaging or platform compatibility | Relevant oldest-supported OS, release build and meaningful content readiness. |
| Network-dependent behavior | Relevant offline, failure and recovery paths. |

Use the consumer's declared supported targets; unresolved support information is
a discovery gap. For shared changes, preserve proof on both affected Android and
iOS targets. A result from one platform cannot prove the other.

### Give documentation and workflow changes relevant checks

A documentation-only PR within an approved mobile program may have zero device
checks when independent diff review confirms no runtime behavior changed. Record
document checks and explicit live/performance non-applicability reasons.
Workflow instructions or executable tooling also need relevant workflow or
command checks; calling them documentation does not remove those checks.

For mobile behavior, preserve real-application regression proof, applicable unit and
performance proof, and existing independent audit lanes. Record the applicability
of each verification block. A blanket `None` or a missing block cannot waive it.
Non-mobile plans continue using their existing unit/live/performance contract.

### Verify a fixed revision and assess later changes

Each verification round records its exact source commit, artifact/build identity,
approved plan and target before dispatch. Workers test that fixed revision even
if the builder continues work elsewhere. Results remain attached to that build.

A later head creates a pending re-verification decision. Apply pstack's existing
patch/build comparison rule to each result before reuse, record the decision and
rerun required checks. Apply the verification-contract comparison separately at
the current main and head SHAs. Its ruling cannot be bypassed by matching builds.
Retain older results as historical evidence rather than silently relabeling them.
Source-only inspection cannot establish that a native result remains valid.

Measure the actual end state the user waits for. A performance method unable to
resolve its declared threshold is inconclusive. Preserve pstack's baseline and
interleaved comparison rules; unrelated scenarios cannot produce a valid ratio.

### Restore devices and expose testing gaps

Record the shared device's relevant state before use, including device identity,
booted devices and any settings the check may change. Restore authorized changed
state and verify it before releasing ownership. Never stop another worker's device
or release a lock while an owning process is live or its ownership is unknown.
An unsuccessful restoration holds release and records a recovery need.

Reuse the earlier local program-control ownership and restoration contract when
it is integrated into the implementation base. Its receipt checks do not perform
device restoration themselves and do not prove observed device behavior.

Report unavailable driving, tools or fault injection as blocked or untested.
When a required path remains inaccessible, record a concrete request for testing
support and present it for an owner decision. Repeated inability stays visible;
it cannot become passed through repetition. Creating consumer debug hooks or
adding testing infrastructure needs its own authorized scope.

## Interfaces and enforcement

Keep the installed `plan-check --binding <binding> <plan>` entry point and public
skill names. Extend the plan grammar with a named `mobile-risk-v1` profile and a
per-PR coverage block only for that explicit profile. Preserve the default grammar
and checks for legacy/non-mobile plans. Malformed or unknown profiles fail.

Use plain Markdown outside comments or code fences so the existing whole-plan
comparison protects profile selection, classifications, risk decisions and check
definitions. The coverage block records these named fields:

- Work type and affected platforms/targets.
- Changed areas and their source/diff evidence.
- Risk IDs, applicability, reasons and covering check IDs per target.
- Live/performance applicability and any approved exemption references.
- Checks with unique IDs, reasons, actions, pass conditions and artifact paths.

Keep a small shared catalog mapping changed areas to risk IDs. Skills explain how
to assess them; deterministic checks validate required fields, IDs, coverage and
target mappings. Independent review establishes whether the declarations match
the actual diff. A structurally valid plan is not proof of completeness, approval
or successful behavior. Missing or misleading declarations remain review findings.

Update the planning template and checker together, including program-level
references to the ten live checks. Load only relevant risk guidance in worker
briefs. Apply the profile's applicability in plan comparison without weakening
its default protection. Record the intentional mobile adaptation in the
consolidation map and regenerate
installed integrity receipts only for reviewed intentional edits.

## Acceptance criteria

| Case | Required result and planned verification |
| --- | --- |
| Approved mobile plan has 12 justified checks | Installed bound plan checker accepts the coverage and leaves the approved check text intact. |
| Navigation change declares navigation coverage but omits process death | Checker rejects the missing required risk/check mapping. Independent review also catches falsely declaring no navigation impact. |
| Storage change omits corruption coverage | Checker rejects the declared storage plan. |
| Relevant check lacks a reason, pass condition, artifact or target | Checker rejects it with a diagnostic naming the PR and check. |
| Shared behavior lists Android proof only | Checker rejects missing affected iOS coverage; evidence checks cannot claim iOS passed. |
| Documentation-only mobile-program PR has justified zero-device coverage | Document checks are accepted; the verdict records live/performance non-applicability, not device passes. Workflow changes still require workflow checks. |
| Builder removes a risk or edits a pass condition | Existing contract comparison holds until the owner approves that exact change; structural validation alone cannot clear the hold. |
| Tested head changes | Older proof cannot clear the new round without a recorded valid reuse decision or fresh proof; changed plan rules still require comparison. |
| Performance method cannot resolve threshold | The result is inconclusive and cannot support a passed performance claim. |
| Device state is changed or owning process is live/unknown | Release holds until restoration and ownership checks succeed. Actual restoration remains a later observed-device trial. |
| Required behavior cannot be driven | Report a visible gap and testing-support request; make no passed claim or unauthorized consumer edit. |
| Legacy/non-mobile plan or migrated mobile plan | Existing default plans retain exact-ten behavior. Migration needs an owner-approved contract change; unknown profiles fail. |

Use external disposable consumers for installed command checks. Record the exact
candidate, inputs, commands, exits and artifacts. Run every README maintenance
check before implementation commits; update test accounting when cases change.
Source and synthetic tests prove only their stated contracts. Mark deferred
Claude Code/Codex and mobile observations as gaps in any completion report.
