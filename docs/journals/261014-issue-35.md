# Setup before mobile proof

## Context

Issue 35 reported that setup skipped a required mobile recipe when a driving
harness existed, suggested unregistered Claude commands, mixed model defaults,
and left playbook paths easy to resolve from the wrong directory.

## Changes and decisions

Keep the existing mobile proof prerequisite. Offer recipe generation independently
of tool availability, reuse the harness, and make refusal leave proof held.
Preserve non-mobile harness behavior and native invocation controls. Correct
setup-chain command examples per host, reconcile the review model default, and
put playbook path ownership in the router's existing instruction.

The review identified that source assertions alone did not satisfy the requested
sample check. Add an opt-in native integration command and CI entry. Its disposable
iOS app has one button feature, an existing XCUITest harness and no recipe. The
check runs setup, accepts its offer, then invokes the generated skill in a fresh
session. Require screenshots to be read, UI assertions to pass and cleanup to
succeed before accepting the run.

## Evidence and reflection

The original plugin fails the native offer assertion. The current source passes
431 Python cases and all maintenance checks. Fixture development exposed an iOS
URL confirmation, Xcode's shutdown ownership and the host's project-source
selection; each was corrected in the test rather than weakening its assertions.
The final native run passed setup, generation and fresh invocation, with two
successful iOS UI proofs and inspected screenshots. Evidence is recorded in the [test report](../../plans/261014-issue-35/reports/261014-issue-35.md).

A harness supplies driving commands. A verification skill supplies the project
recipe and native invocation boundary. Setup must check both where mobile proof
requires both.
