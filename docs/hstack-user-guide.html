hStack User Guide

How to set up hStack in Claude Code, Codex and Cursor, and how to use it when you are stuck, when you debug, and when you build a new feature. Part II shows how to lead hStack like a team: brief it, pick its shape, run it and review it. Written for developers working on Swift/iOS, Kotlin/Android, Kotlin Multiplatform and Compose Multiplatform apps, and for any nontrivial engineering work.

Updated 2026-10-30. Use the switch at the top right to show commands for Claude Code, Codex, Cursor or all of them.

1. Start here

hStack is pstack for mobile development. pstack is poteto's Cursor plugin. hStack carries the same workflow to Claude Code, Codex and Cursor and adds mobile proof rules for four domains: native Swift/iOS, native Kotlin/Android, Kotlin Multiplatform (KMP) shared logic and Compose Multiplatform (CMP) shared UI.

The idea fits in one sentence. You describe what you want and how you will know it is done. hStack picks a playbook, runs the right skills as each step fires, and ends with evidence you can check.

Why use it at all?

An agent left alone tends to do three things: it fixes the first plausible spot, it takes the first design it thought of, and it reports "done" because the code compiles. hStack's playbooks block each of those habits. Bugs are reproduced before they are fixed. Designs are compared before one is chosen. Results are proven on the real app, on the real target, before anyone calls them done. You stop being the person who checks every claim by hand.

How to read this guide

Part I (sections 1 to 14) gets you running. Part II (sections 15 to 24) teaches you to lead hStack like a team. The appendices hold what is verified today and the glossary.

  • First time? Read sections 2 to 5 in order: concepts, setup, commands, then how to talk to the router.

2. How hStack thinks

Five words you will see everywhere

TermWhat it isExample
RouterThe hugues-mode skill. It reads your request, matches it to a playbook and copies that playbook's steps into the todo list./hstack:hugues-mode
PlaybookAn ordered list of steps for one kind of task. There are 23 generic playbooks and 4 mobile ones.Bug fix, Feature, Babysit, mobile-proof
SkillAn instruction file for one job. Playbooks call skills as steps fire. You can also type most of them yourself.how, architect, interrogate, tdd
PrincipleA named rule of judgment. 24 of them. Saying a principle's name redirects the agent mid-task.Laziness Protocol, Prove It Works, Fix Root Causes
EvidenceWhat a run actually produced: commands and exit codes, failing-then-passing tests, screenshots, traces. "It compiles" is never evidence of behavior.RED then GREEN test output, a simulator screenshot

Two kinds of skills

Only setup-hstack is visible to the model by default. Every other bundled skill is user-only, and since 0.5.4 that includes hugues-mode itself. That keeps hStack's share of the host's skill list small. It has three consequences.

  • You start a run by typing the command. A task described without /hstack:hugues-mode$hugues-mode/hugues-mode does not start hStack.
  • You can type any other skill by name. For example /hstack:how$how/how or /hstack:interrogate$interrogate/interrogate.
  • The router reads the rest itself. Inside a playbook, the agent opens each skill's file when a step needs it. You never have to list skills in your prompt.

Who does what

The chat you type into is the coordinator. It plans, reviews diffs and verifies. Code is written by fresh subagents (hugues-agent), and review panels run on several models. A fresh worker for each new round is the default, because chained resumes silently drop instructions. The coordinator owns every worker's output: it reads the diff and writes its own summary instead of passing a worker's claim through. Part II, The lead's job, shows the whole team.

  2. Restart the host

    Quit and relaunch Claude Code, or start a new Codex session. A process that was running before the install or update can keep loading its old cached copy.

  3. Confirm discovery

    In Claude Code, type /hstack: and check that hugues-mode and setup-hstack appear. In Codex, type $ and check for hugues-mode. Since 0.5.4, hugues-mode is user-only, and how Codex lists it under that policy is not yet observed.

    If it is missing, stop

    Do not paste the path of a SKILL.md into the chat as a workaround, copy a skill under another name, or change global settings to force it on. hStack treats those as defects, not fallbacks. Check the install with claude plugin list or your Codex plugin list, and see Troubleshooting.

  4. Pick your models with setup-hstack

    Run this once in each app repository:

    /hstack:setup-hstack $setup-hstack /setup-hstack

    Setup reads which models your host offers, asks for a reasoning budget, shows every role and lets you change any of them. It writes .hstack/models.md at your project root. Every hStack skill reads that file before it picks a subagent's model.

    BudgetEffect
    unlimitedKeeps each role at its listed effort, up to max
    largeEvery role at xhigh
    mediumEvery role at high
    smallEvery role at medium. Fewest tokens.

    Each role lists a Claude model first and a Codex model after it, for example claude-sonnet-5-5 high or gpt-6.1-sol high. Claude models are full IDs. Where Claude Code's agent tool accepts only aliases, setup passes the alias, such as sonnet. Each host runs the first model it accepts, so one file serves every host. In Cursor, setup detects the model ids from the agent tool's own schema in the session and writes the detected id first, keeping the Claude and Codex alternatives after it, so the same file still serves the other hosts. Panel roles (arena runners, architect runners, interrogate reviewers) hold a list, and one subagent runs per entry. A role with no line runs on inherit-parent, which means your chat's own model.

    TierClaude CodeCodexCursorDefault effortUsed for
    Fastclaude-haiku-5-5gpt-6-lunadetected idxhighThe how explorer
    Workhorseclaude-sonnet-5-5gpt-6.1-soldetected idhighCode delegates, investigators, reflect tooling, swarm workers

    A tier fixes the model. A role's effort starts at the tier default and moves with the work. Version 0.5.4 added the Fast tier and folded the old Frontier tier into Judgment, because no default role uses fable. To restore a default, delete that role's line. Rerun setup at any time.

  5. Create a verification skill for your app

    For mobile projects this is required, not optional. The mobile-proof playbook needs a project verify-<app> recipe, even if XcodeBuildMCP or jev-ios-bridge can already drive the app. Setup offers to generate one. Accept. You can also run it yourself:

    /hstack:create-verification-skill $create-verification-skill /create-verification-skill

    The generator studies your repository, not you. It works out how the app launches, what can drive it, and what evidence proves each feature. It writes verify-<app>/ under your .claude/skills/ or .agents/skills/ folder, with Launch, Doctor, Drive, Evidence and Cleanup sections and a feature map. It proves one feature end to end before handing it over. Commit it so every person and agent drives the app the same way.

    Why this pays off the most

    An agent that can check its own work keeps going until the check passes. An agent that cannot hands every result back to you. Keep it honest by running /hstack:maintain-verification-skill$maintain-verification-skill/maintain-verification-skill regularly. It drives every mapped feature and opens at most one PR of proven corrections.

    new in 0.5.5 Setup also offers once to generate a formal verification skill. See the command reference.

5. Talk to hugues-mode

You do not write a spec. You say what is wrong or what you want, plus anything that saves the agent time.

The five things a good prompt carries

PartWhy it mattersExample
The goalWhat is wrong, or what you want"the csv export drops its last row"
The done checkIt must be able to pass or fail. "Make it better" is not a check."done means the 60k-row fixture exports every row"
The proof you wantAsk for an artifact you can inspect"show me the row counts before and after"
What you already knowA log line or repro step saves a search"failing job id is 4812"
Constraints and authorityThese change what the agent does. A plain mode request does not let it edit, build or run your app."repro first", "don't change code yet", "you may run the simulator"

Leave two things out
  • The how. Leave room for a better path than the one you would pick.
  • A list of skills. "Use /how, then /architect, then /arena" usually reorders or drops steps the playbook would have kept. Name a skill only to override a choice.

Hold back your theory of the cause at first, too. A stated guess narrows the search to wherever you pointed.

6. When you are stuck

"Stuck" means different things, and each kind has its own tool. Find your symptom below, then read the matching section.

I don't know which skill to usehugues-help

Answers, gives you a prompt and links its source. Starts nothing.

I don't understand this codehowwhyteach

Mechanics, history, or a full explanation you can argue with.

The agent misread what I wantin-your-own-wordssharpen

Surface the misreading before any code exists. sharpen deepens a thin prompt.

The report is noisy or vaguehugues-mode: restate it

Restate the problem first, change no code.

Every design fights backarchitectarenaPrototype

Compare real candidates instead of polishing the first idea.

Fix after fix keeps failingAttack the PremiseFix Root Causes

Question the shared premise instead of writing fix number three.

I can't tell if the result is rightinterrogateblast-radius

The build or toolchain is brokenbuild-doctor

7. Debug a bug

Say what you observed and ask for a reproduction. The Bug fix playbook supplies the rest: reproduce, root-cause, fix, prove.

Step by step

  1. Describe the symptom and the authority

    State what happens, where, and what the agent may touch.

    /hstack:hugues-mode users get two notifications after a retry. repro first, then fix and verify. you may edit the notification module and run its tests.$hugues-mode users get two notifications after a retry. repro first, then fix and verify. you may edit the notification module and run its tests./hugues-mode users get two notifications after a retry. repro first, then fix and verify. you may edit the notification module and run its tests.
  2. Let it reproduce on the same surface

    The agent drives the app itself: verify-<app> for your app, control-ui for web and Electron, control-cli for CLIs and TUIs. It asks you to reproduce only when it can name a specific reason the surface cannot reach the bug. If the bug will not fire, it synthesizes the trigger or adds instrumentation until it does.

  3. Watch the hypotheses get eliminated

    It lists candidate causes, seeded by how over the subsystem and why for regression history, then takes the split that rules out the most each pass. When state is unclear, it adds logging and reads it as the code runs. It does not guess.

  4. Review the plan for the fix

    If the fix crosses a function boundary, architect runs first. A subagent then implements it with a specific scope.

  5. Check RED then GREEN

    The failing repro lands in git history before the fix. For mobile bugs, a fresh regression worker writes the test and it must fail on the unfixed code. A separate fresh worker then fixes production code, and the same test must pass. When an automated test is impractical, the agent records the concrete reason and an executable runtime reproduction instead.

  6. Read the reply

    It names what was broken, the root cause, the fix and how it was verified, with failing-then-passing output pasted verbatim. "Inconclusive" or a wrong target is flagged, never counted as a pass.

Why this order

Every shipped line traces to runtime evidence. A change that "might help" is a hypothesis, and hypotheses do not ship. When evidence refutes one, the agent reverts what it motivated. The result is the smallest change the evidence justifies, with a regression test that proves the bug existed.

9. Prove it on device

"It compiles" is not evidence. Mobile proof binds a target, a command and the artifacts it produced.

What the proof lane checks

  • Preflight. One real, harmless operation per required tool, under the agent's current settings: the Gradle wrapper's help task, adb devices, xcrun simctl list devices available. A version listing alone does not count.
  • Host baseline. When a tool is blocked, the agent runs the same command outside the agent before touching any settings. If the baseline fails, it reports a host blocker and stops. With the sandbox on, it prints the command for you to run in a plain terminal.
  • Native helpers. Xcode, SwiftPM and Gradle commands run through hStack's native execution helpers. They keep every attempt's full logs and native reports and return a bounded summary. Zero selected tests, stale artifacts or the wrong target never pass.
  • Screen proof. jev-ios-bridge when it is available and permitted. Otherwise a labelled UI-test or device-tooling fallback.
  • Evidence folder. Outside both the plugin and your app repository, so it survives cleanup. It records revision, command, exit code, target identity and artifact paths.
/hstack:hugues-mode prove the save-for-later change with /verify-shop. ios and android. show me screenshots and the test counts per target.$hugues-mode prove the save-for-later change with /verify-shop. ios and android. show me screenshots and the test counts per target./hugues-mode prove the save-for-later change with /verify-shop. ios and android. show me screenshots and the test counts per target.

  • Listing skills in the prompt. The playbook already sequences them.

15. The lead's job

An agent can change a system you have never read. That removes an old barrier and creates a new job. The code is still yours to keep good, and you now supervise a worker that writes code better than you do, in a codebase no one holds in their head.

18. Measure a hundred times, cut once

Prototype to answer a question

The Prototype playbook builds throwaway sketches. Its rules invert most of hStack's. Speed beats polish, code quality does not matter and there are no tests. The rigor sits in choosing the right design cheaply. It also proposes variations you did not ask for.

Architect bigger changes

Poteto's article lists a cross-judge as the third architect phase. In hStack's architect file the cross-judge sits inside arena, so the phases are these.

PhaseWhat happens
1. GroundRun how over every system the new code touches. Add why when the design moves ownership or layering. Skip only for greenfield work.
2. SketchRun arena. Each runner drafts the caller's usage first, then types, signatures and module boundaries with "not implemented" bodies. 3. AgreeOff by default. Say "with checkpoint" or "stop and show me before implementing" to review the design first.
4. ImplementFill in the bodies. The sketch is the contract, and a function that needs a parameter it did not expect is a signal to surface.

The Scrap signal is a pattern, not one incident. These are the tells.

  • The same workaround appears across unrelated code.
  • Several unrelated edge cases each need a special-case branch.
  • Types need escape hatches, such as any, casts or optional fields that are always set.
  • Someone reaches for a lock after the sketch said the state was not shared.
  • Callers must know the abstraction's internal rules.
  • Two or more independent deviations of the same shape appear during Implement.

A few edge cases do not condemn an architecture. Complexity in the data is not complexity in the design.

23. Make the team better over time

A team that repeats its mistakes has a process problem. Poteto's rule is the one hStack encodes as a principle. When you catch yourself writing the same instruction a second time, encode it. If the fix is structural, use only the structural fix, because the instruction is the symptom.

Fix the class of mistake

/hstack:correct $correct /correct

correct reads recent commits, reverts, review comments and workaround comments. It groups the mistakes into classes, and a class counts once it has happened twice. It fixes each class at the highest level that works. The order is architecture, then types, then a lint or CI check whose error names the fix, then a test, then docs last. It proves each new check fails on a real past mistake. It keeps a table in the instruction file that pairs each rule with what enforces it.

Learn from a session

reflect sends three reviewers over a transcript, with judgment, tooling and divergent lenses. A synthesizer returns Accepted, Rejected and Backlog lists. Nothing applies without your approval. It looks for the transcript in an agent-transcripts/ folder. hStack's adapters wire no Claude Code or Codex transcript folder, so when no path resolves, reflect uses a digest of the current session and labels its source and limits. on main, not yet released Approved edits go to a copy under .claude/skills/ or .agents/skills/. reflect never edits the plugin cache and never opens a PR.

Keep the verifier honest

Your verify-<app> skill rots when the app changes. /hstack:maintain-verification-skill$maintain-verification-skill/maintain-verification-skill runs a source wave with one read-only subagent for each feature file, then a required live pass that drives every mapped feature. It ends in one of three outcomes. Clean means no change. Changed means one PR of proven corrections. Blocked means coverage could not finish. It never edits product code. Run it on a schedule you choose.

Defined, not yet observed correct, reflect and whole-map maintenance. The release notes list whole-map maintenance among behaviors the release tests did not establish.

new in 0.5.5 Four user-only skills extend this loop. create-formal-verification-skill generates a project skill that checks a key property, such as a race or an invariant, past what tests reach. maintain-formal-verification-skill keeps it in line with the code and says whether a failure is drift or a bug. statechart draws a flow as a Mermaid chart from a TLA+ model. ketchup-video catches you up as a short silent video of slides.

Two habits close the loop. Fix a misbehaving skill in its own PR instead of working around it in the middle of other work. At the end of an Orchestrate program, move each recurring correction into preferences.md or the brief template.
