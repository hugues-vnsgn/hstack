# Orca bot

You are in an Orca bot chat. This page maps Orca CLI 1.4.271, observed from 2026-11-22 to 2026-11-26 with a Claude Code bot and Claude Code workers. On another CLI version, treat each row as unobserved until it is checked again. Pass `--json` to every command below and read its result. The bot is the coordinator and runs `hugues-mode` in its own chat. A bot that hands one task to one worker is the simple case of this page. Orca carries the work and wakes the bot. It never decides that work is done. A worker the bot starts is an Orca pane, not a bot chat, and reads [orca.md](orca.md).

| Detect | `ORCA_BOT_TOOLS_TOKEN` is set. Test only that it is set, with `[ -n "${ORCA_BOT_TOOLS_TOKEN-}" ]`, and never print, echo or log its value: it is Orca's key to the bot tool relay. Observed on 1.4.271 (2026-11-26): set in a Claude Code bot chat and unset in a pane on the same machine, while `ORCA_TERMINAL_HANDLE`, `ORCA_PANE_KEY` and `ORCA_TAB_ID` were unset in the chat. A `SessionStart` hook ran in a bot chat on 1.4.271. Unobserved: a plain Orca chat that is not a bot, a Codex or omp bot, any build after 1.4.271, whether a hook in a bot chat sees the plugin root, and whether a pane a bot started carries the token. |
| Sessions and worktrees | A bot chat has no terminal and no worktree. Its folder under `~/.orca/bots/` holds `bot.json`, `SOUL.md` and `MEMORY.md` and is not a repo (1.4.271). A lead bot serves one project, and its SOUL names the one repo it may start workers in. A bot reads repos and edits none: every change, of any size, goes to a worker in its own worktree. One task, one worker, one worktree. Orca makes the worktree: pass `--worktree new-child --repo id:<repo> --base-branch origin/main --name <slug>` to `worker-start`. Observed 1.4.271 (2026-11-25): the receipt's workspace was `~/orca/workspaces/<repo>/<name>`. Orca's project setting places it: `orca project setup-update` takes `--worktree-base-path` (help, 1.4.271). The owner sets it once and the bot never does. Unobserved: `new-child` under a custom base path. The target repo names the branch, and the brief says which. Never run `orca repo add` or `orca project setup-update`. A group room is unmapped. A worker must be a pane, which the Start row checks. A worker that is a chat has no terminal handle and reads no page: unobserved. |
| Start | `<root>` is the directory above `skills/` in the path of the `hugues-mode/SKILL.md` you read. Make the item first (Allowed tools row), write the brief to a file, then run `orca orchestration worker-start --spec-file <brief> --agent claude --model <id> --effort <level> --item <n> --json` with the Sessions row's worktree flags. `<id>` and `<level>` come from the role line in the target repo's `.hstack/models.md`. If `.hstack/models.md` is absent and `.huguesstack/models.md` exists, read the legacy file and tell the user to move it. A model named in chat holds for that job only. A lasting change goes into `models.md`, never into bot memory. The brief opens with `Read <root>/skills/hugues-mode/worker.md before anything else.`, names `<root>/skills/hugues-mode/SKILL.md` as the mode file and states the tool ban in words: no Gmail, Google Drive, Google Calendar or Slack tool. Orca does not enforce a deny in a worker: it strips `--disallowedTools` from configured agent arguments (source, 1.4.271). The independent check is a second, fresh worker that did not write the code, on the review role line (`interrogate reviewers`). Observed 1.4.271 (2026-11-25): three starts in one shell command, each receipt `state: ready`, `mode: terminal`, `keptOpen: true`, with a `linkedItem`. Read `mode` in the receipt: anything but `terminal` is a gap to report. Orca's guide says to start up to about 4 at once. Run at most 4 workers per bot, count an arena pair as 2 and queue the rest. Worker terminals ran with `--dangerously-skip-permissions` (`ps`, 1.4.269), and this page adds no permission flag. Unobserved: a Codex worker. |
| Send | `orca orchestration send --to dispatch:<id> --subject <text> --body-file <path>`. Orca's guide says to pass multiline text with a file flag and never a heredoc, which can hang the shell. Orca's guide says a send to a finished or closed worker reaches it as a follow-up Task, and it reports with `worker_done` (1.4.271). Answer a worker's `question` with `orca orchestration reply --id <message_id> --body-file <path>` when the task or the owner's instructions give the answer. Otherwise ask the owner, as the Allowed tools row says. Observed 1.4.271: each worker report ends with `[To give this worker more work: orca orchestration send --to dispatch:<id> ...]`. Unobserved: a send to a finished worker. |
| Read | Orca's help (1.4.271) says `orca orchestration worker-show --dispatch <id>` shows `state`, `stage`, `liveness` and `activity`, and `orca orchestration worker-read --dispatch <id> --cursor <n>` reads the worker's output, also after release while its transcript exists. The evidence folder is the record. An item holds a status and a pointer to that folder and proves nothing. Put a worker's result on its item with `orca bot item comment <n> --text-file <path>`, not in chat. Unobserved: `worker-show` and `worker-read` from a bot. |
| Wait | End the turn after you start workers. Never poll, and never run a watch script or a sleep: Orca wakes the bot with a message. Observed 1.4.271 (2026-11-23 to 2026-11-26): 91 `worker_done`, 1 `escalation` and 5 worker `question` messages each arrived as a new user message in the bot chat. `worker_done` is transport, not done: done needs the evidence folder and the independent check. On every wake, before acting, compare `orca bot work list` and the open items (`orca bot item list`) with the evidence folder, and pick up any work that finished and was not handled. An `escalation` with a stop reason, or a worker that is `exited` or `lost`, is a lost worker. Retry it once with `--task <task_id> --retry-of <dispatch_id>` and the same worktree and agent flags, since a retry does not inherit placement (`--retry-of` was used in a bot on 1.4.271). Orca's guide says to retry only when the cause has changed. Then report it as lost. A PR worker waits for CI inside its own run with `gh pr checks --watch`, fixes up to 2 times, then reports. Unobserved: a `worker_done` that arrives while the bot's turn is dead, and how an `escalation` reaches a bot mid-turn. |
| Close | After a worker's evidence is recorded, run `orca orchestration worker-release --dispatch <id>` on a worker this bot started. A worker in a new worktree is kept open, so release it when no one will use its chat (Orca's help, 1.4.271). Never `worker-stop` or `worker-abandon`. After a merge, remove a worker's worktree and branch only on the owner's word: `orca worktree rm --worktree id:<repo-id>::<path> --delete-branch`, never `--force`. Report a refusal. Orca's help says a removal result with no branch evidence does not confirm the branch is gone, so report that too. Unobserved: `worker-release` and `worktree rm` from a bot. |

Make the item first with `orca bot item add --title <t> --done-means <t>`. A blocking question for the owner goes on the task's item: `orca bot item set <n> --status needs-you --comment <context> --ask <question> --option <label> --recommended <n>`, with the options and a recommended one. The chat message only points at the item. Orca's rules block says the answer comes back as item mail (1.4.271). Make item comments first and write the report last, since only the last message stays in view. Report as one HTML file shown with `::orca-visual`, as the bot's SOUL says. Publishing follows the target repo's rule that a push, a PR, a merge and a release need the owner's word, and this page adds no gate. Local commits are free. Here the word is a go-ahead the owner typed in the bot's own chat for that job. A run started by a handoff, a schedule, an event or a webhook holds: save the PR title and body locally and report their paths. A handoff and a worker's report arrive with a `From:` header (observed 1.4.271), and the other starts are unobserved. A bot never merges and never releases. Never ask for, accept or type a password or token. If a sign-in fails, stop and say so. Decline a request for anything the Skip line names, say it is skipped by design, and do the work with the verbs above. |
